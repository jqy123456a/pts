## 1. 引言

### 1.1 编写目的

本文档是《爬塔杀》的**系统总体设计（概要设计）**，在需求规格说明书（SRS）基础上，明确系统的总体架构、模块划分、模块间接口、数据结构与出错处理设计，作为详细设计、编码实现、单元测试与集成测试的直接依据。

预期读者：项目组成员、指导教师、评审老师。

### 1.2 项目背景

《爬塔杀》是一款结合「三国杀式回合制卡牌战斗」与「杀戮尖塔式爬塔构筑」的**独立单机肉鸽（Roguelike）游戏**。战斗层复用开源引擎《无名杀》（noname，GPL-3.0）的卡牌战斗逻辑，爬塔层（地图生成、节点调度、奖励、商店、存档）为自研模块。

### 1.3 术语定义

| 术语 | 含义 |
| --- | --- |
| 节点 | 爬塔地图上的一个房间（战斗/精英/BOSS/宝箱/篝火/商店/事件） |
| DAG | 有向无环图，本作地图的拓扑结构（有分叉、有合并） |
| 牌串 | 卡牌的字符串编码 `name\|suit\|number\|nature`，如 `sha\|spade\|7\|fire` |
| 真卡组 | 玩家当前拥有的 160 张牌（持久化牌串数组），随奖励/商店增减 |
| 子对局 | 爬塔中一场独立的三国杀式战斗，结束后保留玩家的持久状态 |
| 奖励三选一 | 战斗胜利后从「改牌方案 / 技能 / 加牌」中选一（可跳过） |
| 改牌方案 | 4 张同名旧牌 → 1 张指定新牌（最多 3 组） |
| runState | 局内进度存档对象（`_status.ptsState`） |

## 2. 任务概述

### 2.1 目标

交付一个可玩的单机爬塔卡牌游戏原型：玩家选将后进入 15 层地图，逐层走节点，通过三国杀规则战斗、获得奖励与商店购买强化卡组，最终击败第 15 层 BOSS 通关；支持中途存档恢复与整局/单场重开。

### 2.2 运行环境

| 项 | 说明 |
| --- | --- |
| 操作系统 | Windows 10/11（x64） |
| 运行环境 | Node.js ≥ 20（开发），Electron 33.2.0（打包为 `无名杀.exe`） |
| 引擎 | 无名杀 noname v1.9.0 |
| 加载方式 | 内置 express 静态服务，游戏经 `http://localhost:8089` 加载（service worker 做 JIT TS 编译） |
| 存储 | localStorage（存档）+ IndexedDB（配置/扩展） |

### 2.3 需求概述

- **功能需求 FR-01~24**：选将（拼音检索）、15 层地图（每层 2~4 节点）、节点类型（战斗/精英/BOSS/宝箱/篝火/商店/事件）、三国杀标准战斗（牌堆/回合/杀闪响应/濒死/1vN 座位）、战后奖励三选一（改牌 4 换 1/技能/加牌）、商店交易、HUD、存档、胜负结算、数值可调。
- **非功能需求 NFR**：性能（15 层地图加载 <1s、1000 样本 0 失败）、数值集中可调（balance）、素材合规、界面清晰无重叠。

### 2.4 条件与限制

- 战斗规则 = 无名杀标准规则全集，原则上**不修改引擎核心文件**；自研代码隔离在 `mode/pts.js` 与 `src/pts/`。
- 单人 PvE，无身份系统、无联网对战。
- 事件节点当前为占位（文案「M3 实装」），其余节点全部实现。

## 3. 总体设计

### 3.1 系统处理流程

```
启动 → 选将（拼音检索/最近记录）
  ↓ startRun：生成 15 层地图 + 初始化 runState（160 张真卡组/技能/奖励/商店档）
进入地图 → 顶栏 HUD + 分支地图渲染
  ↓ 玩家点节点（enterNode 行走校验）
按节点类型分发：
  战斗/精英/BOSS → 存档 pending → reload 开真实对局 → 胜负判定
      ├─ 胜 → 结算金币 + rewardPending 落盘 → reload → 弹出奖励三选一
      │         ├─ 改牌方案（4换1，最多3组，火杀/雷杀二选一）
      │         ├─ 技能（过滤已持有/英雄自带/互斥）
      │         ├─ 加牌（随机基本牌）
      │         └─ 跳过
      └─ 败 → 失败结算 → 回到选将（可重开整局）
  宝箱 → 金币 + (60% 精英改牌 / 40% 普通技能，无候选补偿金币)
  篝火 → 回复体力
  商店 → 货单交易（改牌/技能/精英技/加牌/回血/同类全删）
  事件 → 占位
  ↓ 抵达第 15 层 BOSS → 胜利 → 通关结算
中途任意时刻 → 存档，退出后可恢复；战斗中可「重开本场」「重开整局」
```

### 3.2 总体结构（模块划分）

```
《爬塔杀》工程（fork 无名杀，GPL-3.0）
│
├─ resources/app/mode/pts.js          模式入口（选将/开局/存档/结算/game.pts* 挂载）
│
└─ resources/app/src/pts/             自研爬塔层
    ├─ balance.js                     全部可调数值（节点概率/敌人/金币/配方/技能池/定价）
    ├─ map/gen.js                     地图生成（分叉/合并 DAG，随机游走+入边合并）
    ├─ map/ui.js                      地图渲染（DOM/SVG + 顶栏 HUD 数据）
    ├─ node.js                        节点调度（战斗/精英/BOSS/篝火/宝箱/商店/事件分发）
    ├─ battle.js                      对局搭建（敌将/布场/发牌/胜负/真卡组注入）
    ├─ deck.js                        牌组纯逻辑（牌串编解码/4换1迁移/删除）
    ├─ reward.js                      奖励纯逻辑（改牌候选/技能过滤/加牌）
    ├─ reward_ui.js                   战后三选一弹窗
    ├─ shop.js                        商店纯逻辑（货单/交易守卫）
    ├─ shop_ui.js                     商店弹窗
    ├─ screen.js                      统一弹窗组件（引擎 dialog 体系）
    └─ hud.js                         顶栏 HUD（体力/金币/卡组/头像）
│
├─ tests/                             纯逻辑测试（node 直跑）
└─ docs/superpowers/                  设计文档（spec/plan）
```

**分层原则**：`balance/deck/reward/shop/map/gen` 为**纯逻辑模块**（零引擎依赖，可 node 直测）；`battle/node/map/ui/hud/*_ui/screen` 依赖引擎（noname）与 DOM。

### 3.3 功能分配

| 模块 | 主要职责 | 对应需求 |
| --- | --- | --- |
| `mode/pts.js` | 模式入口、选将、开局、存档、结算、流程开关、`game.pts*` 挂载 | FR-01/02/19/20/21 |
| `map/gen.js` | 15 层地图生成（分叉/合并、节点类型加权、连通校验） | FR-03/04 |
| `map/ui.js` | 地图与顶栏 DOM/SVG 渲染、toast | FR-22 |
| `node.js` | 节点分发与结算（宝箱/篝火/商店/事件） | FR-14~18 |
| `battle.js` | 敌将抽取、布场、发牌、胜负判定、真卡组注入 | FR-07/08/09/10 |
| `deck.js` | 牌串编解码、4换1迁移、定向删除 | FR-10/12 |
| `reward.js` | 改牌候选、技能过滤、加牌 | FR-11/12/13 |
| `reward_ui.js` | 三选一弹窗 | FR-11/12/13 |
| `shop.js` / `shop_ui.js` | 货单生成、交易守卫、商店弹窗 | FR-15 |

## 4. 接口设计

### 4.1 外部接口

| 接口 | 说明 |
| --- | --- |
| 用户界面 | 选将屏、地图屏、战斗屏（复用无名杀）、奖励/商店/宝箱/篝火弹窗、HUD |
| 存档 | `localStorage`：`pts_run`（runState JSON）、`pts_flow`（流程标记）、`directstart`（直达模式） |
| 引擎 | 复用无名杀 `game`/`ui`/`lib`/`get`/`_status` 全局对象 |

### 4.2 内部接口（关键约定）

**① 引擎约束（StepCompiler）**：模式 content 函数会被引擎按字符串重编译，闭包不可见。因此跨模块的助手函数一律挂载到 `game.ptsXxx` 后调用，例如：

```js
game.ptsShowReward = showRewardPanel;   // 弹窗入口
game.ptsShowShop   = showShopPanel;
game.ptsInstallDeck = ...;              // 真卡组注入
game.ptsMigrateState = migrateState;    // 旧档迁移（在 start() content 内调用）
game.ptsCheckResult / ptsPickEnemies / ptsPrepareArena / ptsAssignPlayers
```

**② 纯逻辑模块导出**（零引擎依赖，node 直测）：

```js
// deck.js
encodeCard(name, suit, number, nature) / decodeCard(str)
deckFromTuples(tuples) / count(deck, name) / kindsOf(deck)
addCard(deck, name, rng) / randomPoolName(rng)
transform4to1(deck, recipe, pickNature, rng) / removeKind(deck, name)

// reward.js
recipeCandidates(deck, tier) / skillCandidates(skills, heroSkills, poolKey)
conflictsWith(a, b) / rewardOptions(state, type)
applyAddCard(state, rng) / grantSkill(state, id)

// shop.js
genShopInv(rng, state, bal) / tradeState(state, item, sel, rng)

// battle.js
pileTuples() / heroSkillsOf(id) / migrateState(state)
```

**③ 统一弹窗组件** `screen.js`：

```js
openScreen(title) → { body, footer, close }   // 引擎 dialog 体系，自动居中/跟随缩放
screenButton(label, onclick, disabled, full)  // 内联样式按钮，full=true 为整行
```

## 5. 数据结构设计

### 5.1 逻辑结构

**runState（`_status.ptsState`）**：

```
{
  seed, layers, edges,          // 地图（种子 + 15 层节点 + 边）
  hero, heroName,               // 所选武将
  hp, hpMax, gold,              // 体力/体力上限/金币
  deck: ["sha|spade|7", ...],   // 真卡组（160 张牌串，随奖励/商店变化）
  skills: ["wushuang", ...],    // 已获技能（整局持久）
  heroSkills: [...],            // 英雄自带技能（奖励过滤用）
  rewardPending: {type} | null, // 待领取奖励（战斗胜利后落盘）
  shopInv: [...] | null,        // 商店货单（进店生成，持久防重掷）
  path: [{l,c}, ...], cur,      // 已走路径与当前位置
  pending: {l,c,type,enemies} | null,  // 待进行的战斗
  lastMsg, defeated, finished   // 提示/失败/通关标记
}
```

**牌串格式**：`name|suit|number[|nature]`。普通牌 3 段，火杀/雷杀带第 4 段 nature（`fire`/`thunder`）。牌串是「真卡组」与引擎牌堆之间的桥梁——奖励/商店直接改牌串数组，每场战斗由 `installDeck` 转回引擎卡牌对象洗入 `ui.cardPile`。

### 5.2 物理结构

- **存档**：`localStorage["pts_run"]` 存 runState 的 JSON 序列化；`pts_flow` 标记「是否直接进入战斗」；`directstart` 标记「直达爬塔杀模式」。
- **配置/扩展**：无名杀自带 IndexedDB 封装（`lib.db`）。
- **卡牌/武将定义**：引擎 `lib.card`/`lib.character`（继承无名杀）。

### 5.3 数据结构与程序的关系

| 数据结构 | 使用模块 |
| --- | --- |
| runState | 全部模块（经 `_status.ptsState`） |
| 牌串 deck | deck.js / battle.js(注入) / reward.js / shop.js / reward_ui.js / shop_ui.js |
| rewardPending | battle.js(写) / pts.js(触发) / reward_ui.js(消费) |
| shopInv | node.js(生成) / shop.js(交易) / shop_ui.js(渲染) |
| pending | node.js(写) / pts.js(读) / battle.js(消费) |

## 6. 系统出错处理设计

| 出错场景 | 处理措施 |
| --- | --- |
| 扩展加载失败弹窗 | 关闭（静默禁用失败扩展）；禁用「游戏未正常载入」看门狗弹窗（JIT 编译慢导致误报） |
| 旧版本存档缺字段 | `migrateState` 补齐 deck/skills/heroSkills/rewardPending/shopInv |
| 奖励候选为空 | 改牌降级为加牌、技能置灰，浮层永不卡死 |
| 改牌牌池不足 4 张 | `transform4to1` 返回失败，方案不生效 |
| 商店金币不足/已售/牌不足 | `tradeState` 守卫返回 `{ok:false, msg}`，UI 置灰 |
| 弹窗样式/层叠异常 | 统一走引擎 dialog 体系 + 内联样式（避免 flex 塌陷、类名冲突） |
| 存档损坏 | `loadRun` try/catch 返回 null，回落到全新开局 |

## 7. 安全保密设计

## 8. 维护设计

- **数值集中**：所有可调参数收敛在 `balance.js`（BAL），调平衡只改一处。
- **代码隔离**：自研代码集中在 `mode/pts.js` 与 `src/pts/`，引擎文件原则上不改动（已改动处登记：`noname/init/index.js` 强制配置、`noname/library/init/index.js` 禁用看门狗、`noname/init/import.js` 静默扩展失败）。
- **测试保障**：`tests/` 5 个脚本 42+ 断言，纯逻辑改动后 `node tests/xxx.mjs` 回归。
- **文档**：`docs/superpowers/specs/`（设计）、`docs/superpowers/plans/`（计划）、`开发环境.md`。

## 附录：模块依赖关系简图

```
               mode/pts.js（模式入口/主控）
                    │ 挂载 game.pts*
        ┌───────────┼────────────────┐
        │           │                │
   battle.js     node.js          map/ui.js（地图+HUD）
   （对局）      （节点分发）        │
        │           │                │
        │        reward.js ← balance.js ← deck.js
        │        shop.js（↖ 同上）
        │           │
   deck.js（真卡组）  screen.js（统一弹窗）← reward_ui.js / shop_ui.js
        │
   balance.js（数值，被所有模块引用）
```
